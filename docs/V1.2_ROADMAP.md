# v1.2 Architecture Roadmap

Proposal only. This document does not change product behavior.

The Multi-Model AI Orchestrator is currently **v1.1.0**: a Windows-first local CLI that routes coding work to Cursor Agent, Codex, and Gemini/Antigravity, with optional GitHub Issue automation that stops at ready-for-human-merge.

v1.2 should keep those invariants:

- Never auto-merge or auto-publish.
- Never interpolate user task text into shell strings.
- Isolated Git worktrees under the per-user runtime directory, not in the user's project.
- Manual model selection never silently falls back.
- Independent project tests remain the source of verification, not agent claims.

---

## 1. Current architecture

### Local run path

```text
Cursor Chat  →  /ai or /ai-team skill  →  ai-orchestrator CLI
                                              ↓
                                           Router
                                    CURSOR | CODEX | GEMINI | TEAM
                                              ↓
                                    Isolated git worktree
                                              ↓
                         Independent tests + optional local commit
```

**TEAM** is sequential and pinned to one verified worktree: Cursor plans, Codex implements, the orchestrator runs tests, Gemini reviews read-only, Codex fixes inside a bounded loop.

Runtime artifacts (`runs/`, `worktrees/`, GitHub issue state) live under `%LOCALAPPDATA%\MultiModelAIOrchestrator\`. Configuration precedence is CLI argument → environment → user config → smart auto → built-in default.

### GitHub automation (v1.1)

Optional, default off. Assisted mode is label-gated (`ai-auto` from a trusted actor):

```text
Issue  →  authorize  →  implement  →  local tests
       →  push AI branch  →  one PR  →  GitHub CI
       →  bounded fix loop  →  READY_FOR_HUMAN_MERGE
```

Supporting pieces already in tree:

| Piece | Role today |
| --- | --- |
| State machine (`github-state.mjs`) | Canonical transitions, crash-safe persist, issue lock |
| Simulator (`github simulate --fixture`) | Full lifecycle without the network |
| Event log (`github-events.mjs`) | Per-issue JSONL of automation actions |
| Doctor (`github doctor --repo --issue`) | State, branch, PR, CI, auth, runner |
| Worker isolation | One run worktree; sibling worktrees rejected; HEAD SHA checkpoint |

Concurrency is **one lock per issue**. A second process on the same issue reports busy. There is no repo-wide queue and no parallel issue workers.

### Model selection today

Automatic selection picks a capability tier (plan / implementation / review / fix) from the discovered registry. Manual `--model-id` / stage flags fail closed if the id is unavailable. Routing itself is mostly keyword classification plus explicit `--mode`.

### Human control today

- Local: no push, no merge.
- GitHub: `ai-stop`, untrusted-actor block, `HUMAN_REVIEW_REQUIRED`, `READY_FOR_HUMAN_MERGE`.
- Merge and publish stay human-only even if config says `autonomous`.

## 2. Limitations

These are product limits of v1.1, not bugs to paper over in this release.

1. **No queue.** A new `ai-auto` on a second issue while another run is active is either skipped, races the operator, or requires a later manual `github resume`. There is no ordered backlog.
2. **No multiple concurrent issues.** Isolation exists at the worktree and issue-lock level, but the engine does not schedule two implementations at once, and GitHub CI wait loops occupy a process.
3. **Routing is brittle.** Keyword lists (English/Persian) plus `--mode` do not score task risk, size, or whether TEAM is actually warranted.
4. **No cost tracking.** Worker duration is logged; token/USD cost is not. Operators cannot budget a repo or a week of automation.
5. **No AI confidence scoring.** TEAM review is a PASS / NEEDS_FIXES / UNKNOWN line from Gemini. There is no numeric confidence, disagreement signal, or “ask a human” threshold besides CI attempt limits.
6. **Human approval is coarse.** Approval is GitHub labels plus a terminal stage. There is no first-class approve/reject command, no required checklist, and no dual-control for high-risk repos.
7. **Audit logs are incomplete.** GitHub actions have structured events. Local TEAM runs have `meta.json` / `checkpoint.json` / `workspace-trace.json`. There is no queryable, retention-policy audit stream across local + GitHub, and no signed trail of who authorized a run.
8. **CI wait is a poll loop** in-process (about 15s). A crash is recoverable via resume, but the process cannot park and yield to another issue.
9. **TEAM resume is a checkpoint, not a product command.** After process kill, `checkpoint.json` plus the worktree are enough to re-pin the workspace. There is no `ai-orchestrator run --resume-run <id>` that continues the next TEAM stage.
10. **Windows-first remains the only claimed host.** Any v1.2 scheduler must keep cmd/PowerShell spawning rules and worktree paths first-class.

## 3. Proposed improvements

Do not implement these in v1.1. Each item should land as its own design + tests, still stopping at ready-for-human-merge.

### 3.1 Queue system

Add a durable **repo queue** next to issue state (same runtime directory, no secrets).

Suggested jobs: `authorize`, `implement`, `push-pr`, `watch-ci`, `fix`, `reconcile`.

Rules:

- Enqueue on trusted `ai-auto`; dequeue only after the previous job for that issue reaches a safe boundary.
- Persist job id, issue, stage, attempt, `createdAt`, `leaseUntil`.
- Recover leases after crash the same way issue state recovers `unsafePushPending`.
- `github doctor` and `github status` should show queue position.
- Simulator fixtures grow a `queued-second-issue` scenario that must not start a second implementation until the first job yields.

### 3.2 Multiple concurrent issues

Once the queue exists, allow **N concurrent issues per repo** (config, default 1).

Constraints:

- Each issue keeps its own worktree, branch, lock, and event log.
- Source repo fingerprint checks stay per source checkout; workers still cannot bind a sibling run's worktree.
- Global cap on concurrent Codex/Cursor/Gemini processes (Windows handle/sandbox cost).
- Never share a worktree across issues. Never push `main`. Never force-push.

Start with `max_concurrent_issues: 1` compatible with v1.1, then raise to 2–3 behind config.

### 3.3 Model selection strategy

Keep the current precedence and the “manual never silent-fallback” rule.

v1.2 strategy layer on top of AUTO only:

| Signal | Use |
| --- | --- |
| Task class (fix / UI / review / architecture) | Existing router, plus size/risk hints |
| Capability profile (strong / balanced / cheap) | Existing TEAM stage profiles |
| Cost budget remaining | Prefer cheaper id in the same tier |
| Recent failure rate of an id | Temporarily demote in AUTO |
| Explicit issue labels | Already mapped; do not override MANUAL |

Add a logged `selectionStrategy` object: requested, resolved id, tier, reason, fallbacks considered (AUTO only). Manual still errors if the requested id is missing.

### 3.4 Cost tracking

Record per worker invocation:

```text
{ runId, issue, worker, model, durationMs, inputTokens?, outputTokens?, estimatedUsd, source }
```

Store beside `usage.json` and GitHub event JSONL. CLI: `ai-orchestrator usage --repo … --since …`.

Estimates may use a local price table; missing token counts stay `unavailable` rather than inventing numbers. Cost must never appear in GitHub comments as a secret-bearing dump.

### 3.5 AI confidence scoring

After implementation and after Gemini review, persist a **confidence record** (0–1 plus reasons). Inputs can include:

- Independent test status (hard gate; FAIL ⇒ confidence floor).
- Gemini decision (PASS / NEEDS_FIXES / UNKNOWN).
- Diff size / file count vs the plan.
- Whether a fix round was required.
- Disagreement between tests PASS and review NEEDS_FIXES.

Policy (proposal):

- Below `confidence.min_merge_ready` (config) → `HUMAN_REVIEW_REQUIRED` even if CI PASS.
- Below `confidence.min_auto_fix` → do not spend another fix attempt; ask a human.
- Never use confidence to auto-merge.

### 3.6 Human approval workflow

Promote approval from “labels + terminal stage” to an explicit workflow:

1. `READY_FOR_HUMAN_MERGE` remains the automation ceiling.
2. New commands (names TBD): `github approve --issue n`, `github reject --issue n --reason …`.
3. Optional required checklist in `.github/ai-orchestrator.yml` (tests, review, security note) that doctor/status can show.
4. High-risk routing (auth, migrations) can require a second trusted actor before implementation starts (`approval.require_before_implement`).
5. Reject returns to `FAILED` or `HUMAN_REVIEW_REQUIRED` without deleting the PR.

v1.2 still does not merge. Approve means “human accepted the PR as merge-ready,” which may only add a label/comment.

### 3.7 Audit logs

Unify local run traces and GitHub events into one **append-only audit stream** per repo:

- Who (GitHub actor or local user name, never tokens).
- What (action + stage).
- Which issue / run id / commit SHA / PR.
- Result and confidence/cost summaries.
- Hash-chain or at least monotonic sequence numbers so truncation is visible.

Retention in user config (for example 30 days). `github doctor` should point at the audit file. Redaction rules from CI logs stay in force.

Export: `ai-orchestrator audit --repo owner/name --issue n` (read-only).

## 4. Suggested v1.2 delivery order

1. Durable queue + lease recovery (unblocks everything else).
2. Optional `max_concurrent_issues` with isolation tests.
3. Unified audit stream (extend `github-events`, include local TEAM checkpoints).
4. Cost records + usage CLI.
5. AUTO-only selection strategy + logged reasons.
6. Confidence scoring wired to `HUMAN_REVIEW_REQUIRED`.
7. Explicit approve/reject commands and optional pre-implement approval.

Each slice should ship with simulator fixtures and `npm test` green, same as v1.1.

---

## 5. Out of scope for v1.2

- Auto-merge, auto-deploy, or enabling `publish`.
- Cloud-hosted orchestrator as a required service.
- Replacing Git worktree isolation with in-place default.
- Silent model fallback for MANUAL selection.
- Treating agent stdout as proof that tests passed.
